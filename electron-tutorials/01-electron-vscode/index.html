    Code OSS / VS Code：Electron 43.8.3 的工业级目录与文档索引

    参考 checkout：Code OSS 1.145.0，commit d0adb05e；Electron 43.8.3，Node 24.22.1。作者仓库中的参考路径为 .reference/vscode，下文路径相对该 Code OSS 仓库；前置教程见 00-electron-init.md。

    这篇索引分成两部分：第一部分看 Code OSS / VS Code 的目录树、分层、进程模型与构建链；第二部分按阅读顺序进入仓库内开发文档、instructions 与 skills。它适合在读完初始化教程后，继续理解一个工业级 Electron 项目如何组织代码、构建与测试。

    下面的数字来自参考 checkout 的 find、du、tree 和 git ls-files 统计；目录树排除了 .git 与 node_modules。

    1. 一张图看顶层

    code-oss/
├── src/                  # 231M，应用 TypeScript 源码
│   ├── vs/               # 核心分层：base → platform → editor → workbench → sessions
│   ├── vscode-dts/       # 扩展 API 声明，含 185 个 proposed API
│   └── typings/          # 全局类型补充
├── extensions/           # 108M，96 个内建扩展目录，95 个 package.json
├── build/                # 15M，构建、打包、CI、checksums、平台脚本
├── resources/            # 11M，各平台图标、桌面文件、安装器资源
├── cli/                  # 1.9M，Rust 编写的 code CLI
├── remote/               # 120K，远程与 Web 端的依赖清单
├── test/                 # 2.4M，单元、集成、冒烟、自动化、Monaco 测试
├── scripts/              # 844K，开发启动与测试脚本
├── .github/              # 2.2M，CI workflow、指令、技能与 PR 模板
├── .devcontainer/        # 32K，Node 24-bookworm 开发容器
├── .vscode/              # 编辑器任务、调试配置、自举扩展

└── README.md / CONTRIBUTING.md / SECURITY.md / AGENTS.md

    code-oss/ 是示意根目录，实际请替换成你的 checkout 路径。

    仓库共有 21,284 个受 Git 管理的文件。src/vs 本身有 2,842 个目录、12,994 个文件，是绝对的主体；extensions/ 有 1,573 个子目录、6,692 个文件；build/ 有 65 个目录、507 个文件。这个体量让应用源码、内建扩展、构建脚本、平台资源、测试各自拥有顶层目录，边界清晰。

    2. 顶层目录的职责

    路径 职责 阅读入口
    src/vs/ 编辑器与工作台的核心实现 src/vs/workbench/workbench.desktop.main.ts
    src/vscode-dts/ 扩展 API 的公开与 proposed 类型声明 vscode.d.ts、vscode.proposed.*.d.ts
    extensions/ 随应用发布的内建扩展 extensions/git/package.json、extensions/typescript-language-features/
    build/ 编译、下载、打包、签名、发布、校验 build/gulpfile.vscode.ts、build/lib/electron.ts
    resources/ Windows/macOS/Linux/Server 的图标与安装资源 resources/linux/code.desktop
    cli/ 独立 Rust CLI，负责 code 命令、隧道、桌面启动 cli/Cargo.toml、cli/src/commands.rs
    remote/ 远程与 Web 端的依赖清单；源码在 src/vs/server 与 src/vs/code/browser remote/package.json
    test/ 多层级测试与测试基础设施 test/README.md
    scripts/ 开发启动、测试、性能与辅助脚本 scripts/code.sh、scripts/test.sh
    .github/ PR CI、安全扫描、agent 指令与技能 .github/workflows/pr.yml、.github/instructions/
    .devcontainer/ 可复现的开发容器 .devcontainer/Dockerfile
    product.json 产品名、协议、下载 feed、内建扩展清单 product.json

    remote/ 只放依赖清单，容易误读。远程服务器的实际 TypeScript 源码在 src/vs/server/node/，Web 端的启动代码在 src/vs/code/browser/ 与 src/vs/workbench/workbench.web.main.ts。remote/web/package.json 是 Web 客户端的依赖根。cli/ 则是单独的 Rust 工程，与 Electron 主进程通过命令行和 RPC 协作。

    3. src/vs 的分层

    .github/instructions/source-code-organization.instructions.md 给出了权威的分层顺序：

    base → platform → editor → workbench
                              ├── code（Electron/桌面入口）
                              ├── server（远程入口）
                              └── sessions（Agents Window，可导入 workbench）

    code 与 server 是应用入口层；sessions 位于 workbench 之上，可以导入 workbench 及以下各层，workbench 不能反向导入 sessions。

    层 规模（参考 checkout） 角色
    src/vs/base/ 17M，563 文件 通用工具、事件、生命周期、URI、DOM、IPC 基础设施
    src/vs/platform/ 67M，4,329 文件，112 个服务目录 依赖注入与跨层服务：文件、配置、存储、扩展管理、终端、远程、遥测
    src/vs/editor/ 16M，1,308 文件 Monaco 编辑器核心、语言特性、独立编辑器入口
    src/vs/workbench/ 104M，5,545 文件，102 个 feature contribution 工作台 UI、布局、服务、扩展 API 宿主
    src/vs/code/ 600K，27 文件 Electron 主进程、渲染进程引导、共享进程、Node CLI 入口
    src/vs/server/ 380K，30 文件 远程开发服务器入口与远程扩展宿主
    src/vs/sessions/ 26M，1,189 文件，35 个 contribution Agent Sessions 窗口，位于 workbench 之上

    code 层的文件数很少，这是有意为之：Electron 主进程只负责应用生命周期、窗口、服务和进程编排，真正的编辑器与工作台能力放在 platform、editor、workbench。src/vs/code/electron-main/main.ts 是主进程入口，app.ts 里的 CodeApplication 负责启动服务、创建窗口和 IPC；src/vs/code/electron-main/ 只有两个核心文件。

    3.1 目标环境目录

    每一层内部再按运行环境拆分：

    目录 可用 API 典型用途
    common/ 基础 JavaScript 纯逻辑、协议、数据结构
    browser/ Web/DOM 渲染进程与 Web 版共享的 UI
    node/ Node.js 主进程、CLI、服务器、扩展宿主
    electron-browser/ Browser + 有限 Electron IPC Electron 渲染进程
    electron-utility/ Electron utility process 共享进程、扩展宿主等后台进程
    electron-main/ Electron 主进程 API 窗口、生命周期、原生集成

    src/vs/code/ 的目录正好对应 Electron 的进程边界：

    • electron-main/：主进程，main.ts 与 app.ts。
    • electron-browser/：渲染进程的 workbench 引导。
    • electron-utility/：共享进程，sharedProcessMain.ts 以及清理、扩展管理、本地化等 contribution。
    • node/：CLI 参数与 Node 入口。
    • browser/：Web 版的工作台引导。

    这把“代码放在哪个进程运行”变成目录结构的一部分，阅读时不必靠运行时判断。

    3.2 contribution 模型

    src/vs/workbench/contrib/ 下有 102 个 feature 目录，覆盖 git、debug、search、terminal、notebook、chat、mcp、remote 等。每个 contribution 有一个 .contribution.ts 入口，跨 contribution 的依赖通过各自的 common API 完成，不能直接进入对方内部实现。src/vs/workbench/workbench.common.main.ts、workbench.desktop.main.ts、workbench.web.main.ts 是三个入口，只有被入口引用到的代码才会加载。

    src/vs/workbench/services/ 放工作台级服务实现，src/vs/workbench/api/ 放扩展 API 的宿主侧与扩展宿主侧。platform 层提供 112 个服务目录，通过构造函数注入和 createDecorator 标识符组合。分层、目标环境、contribution 入口三者一起，构成了 VS Code 的模块边界。

    4. Electron 进程模型

    VS Code 的目录树直接映射 Electron 的多进程模型：

    ┌────────────────────────────────────────────────────────────┐
│ Electron main process                                     │
│ src/vs/code/electron-main/main.ts → app.ts → CodeApplication│
│ 负责：应用生命周期、窗口、菜单、协议、更新、服务注册         │
└───────────────┬───────────────────────┬────────────────────┘
                │ BrowserWindow          │ utilityProcess
                ▼                        ▼
┌──────────────────────────────┐  ┌──────────────────────────┐
│ Renderer / Workbench         │  │ Shared process           │
│ electron-browser/workbench   │  │ electron-utility/        │
│ workbench.desktop.main.ts    │  │ sharedProcessMain.ts     │
│ src/vs/workbench/browser/    │  │ 扩展管理、用户数据同步、   │
│ workbench.ts                 │  │ 隧道、清理任务            │
└───────────────┬──────────────┘  └──────────────────────────┘
                │ RPC
                ▼
┌──────────────────────────────┐
│ Extension host (utility)     │
│ ExtensionHostStarter         │
│ workbench/api/node/          │
│ extensionHostProcess.ts      │
│ mainThread* ↔ extHost*       │
└──────────────────────────────┘

    主进程入口的调用关系：

    1. src/vs/code/electron-main/main.ts 创建服务、解析启动参数、处理单实例与 IPC。
    2. src/vs/code/electron-main/app.ts 的 CodeApplication 初始化应用、创建窗口、注册协议与更新。
    3. 窗口加载 src/vs/code/electron-browser/workbench/workbench.ts，进入 src/vs/workbench/electron-browser/desktop.main.ts。
    4. src/vs/workbench/workbench.desktop.main.ts 引入 common、desktop contribution 和 electron-browser 服务。
    5. src/vs/workbench/browser/workbench.ts 创建 Workbench，布局 parts、视图、编辑器与状态栏。

    扩展宿主的启动点在 src/vs/platform/extensions/electron-main/extensionHostStarter.ts：它通过 WindowUtilityProcess 启动 vs/workbench/api/node/extensionHostProcess，并把 type: 'extensionHost' 的进程注册进主进程生命周期。src/vs/workbench/api/ 共有 367 个文件，browser/mainThread*.ts 与 common/extHost*.ts 成对出现，负责把 VS Code 内部服务映射为扩展 API。

    IPC 基础设施集中在 src/vs/base/parts/ipc/：common 定义通道与协议，node 提供进程间 socket，electron-main 与 electron-browser 提供 Electron 适配，src/vs/platform/ipc/ 提供主进程服务通道。共享进程、扩展宿主、窗口之间都通过这套通道通信。

    远程与 Web 复用同一套 workbench：

    • src/vs/server/node/ 提供远程服务器、远程扩展宿主、文件系统与终端通道。
    • src/vs/workbench/workbench.web.main.ts 是 Web 入口。
    • src/vs/code/browser/workbench/workbench.ts 是浏览器引导。
    • remote/package.json 与 remote/web/package.json 只负责依赖清单。

    5. 内建扩展

    extensions/ 下有 96 个一级目录，95 个 package.json。它们随应用一起发布，覆盖语言语法、语言特性、主题、调试、Git、GitHub、终端建议、Markdown、Notebook、Copilot 等。代表性结构：

    extensions/
├── git/
│   ├── package.json       # contributes: commands/keybindings/menus/views
│   ├── src/
│   └── ...
├── typescript-language-features/
│   ├── package.json
│   ├── src/
│   └── server/
├── theme-defaults/
├── copilot/
└── ...

    extensions/git/package.json 声明 main、engines.vscode、activationEvents 和 contributes，与 marketplace 扩展遵循同一套 API。extensions/package.json 是共享依赖根，包含 typescript、@parcel/watcher、esbuild，并用 allowScripts 放行 @parcel/watcher 与 esbuild 的安装脚本。构建时，build/gulpfile.extensions.ts 与 build/npm/postinstall.ts 负责编译、安装和打包这些扩展。

    内建扩展的数量说明了 VS Code 的功能组织方式：核心 workbench 提供平台能力，语言与工具能力尽量放在独立扩展包里。扩展宿主通过 vscode.d.ts 与 workbench/api 提供稳定边界，内建扩展与第三方扩展共享同一套协议。

    6. 构建、版本与供应链

    6.1 Electron 版本的实际来源

    参考树的 Electron 版本不在根 package.json 的 devDependencies 里。权威来源是 .npmrc：

    disturl="https://electronjs.org/headers"
target="43.8.3"
ms_build_id="15784459"
runtime="electron"
ignore-scripts=false
build_from_source="true"
legacy-peer-deps="true"
timeout=180000

    build/lib/electronVersion.ts 用正则从 .npmrc 读取 target 与 ms_build_id；build/lib/electron.ts 调用 @vscode/gulp-electron 下载对应平台的 Electron 归档；build/checksums/electron.txt 记录所有 43.8.3 制品的 SHA-256，包括 electron-v43.8.3-*.zip 与 chromedriver-v43.8.3-*.zip。build/npm/electronTypes.ts 还按同一版本下载 electron.d.ts，并用 checksums 校验。

    这条链路解释了为什么根 package.json 不需要 electron 依赖：Electron 二进制由构建系统下载到 .build/electron，类型声明下载到 .build/typings，两者都由 .npmrc 的 target 驱动。build/lib/electronVersion.ts 还会比较 .build/electron/version 与目标版本，决定是否重新下载。

    6.2 Node 版本

    .nvmrc 为 24.22.1。build/npm/preinstall.ts 会读取它，要求当前 Node 的主版本一致、次版本不低于 .nvmrc，并在 npm 主版本达到 13 时拒绝安装。.devcontainer/Dockerfile 使用 mcr.microsoft.com/devcontainers/typescript-node:24-bookworm，把 Node 24 与 Debian bookworm 固化到开发容器里。根 package.json 没有 engines 字段，Node 约束由 .nvmrc 与 preinstall 脚本共同承担。

    6.3 npm 与多安装根

    参考树使用 npm，根 package-lock.json 是 lockfileVersion 3，包含 1,670 个包条目。仓库里共有 63 个 package-lock.json，build/npm/dirs.ts 列出 54 个安装根：根目录、build、build/rspack、build/vite、extensions、多个带依赖的扩展、remote、remote/web、test/*、.vscode/extensions/*。build/npm/postinstall.ts 依次在这些目录执行 npm 安装，并用 installStateHash.ts 做增量跳过。

    这是“多安装根”模型。每个扩展或测试目录保留自己的锁文件，根锁文件负责主应用依赖。VS Code 用 build/npm/check-allow-scripts.ts 检查安装脚本：它在每个 package.json 所在目录运行 npm approve-scripts --allow-scripts-pending，发现未列入 allowScripts 的脚本就失败。根 package.json 的 allowScripts 有 29 项，其中 6 项显式设为 false；extensions/package.json 与 remote/package.json 也各自维护允许列表。

    这套机制与 pnpm 12 的 allowBuilds 目标一致：安装脚本必须被显式批准。VS Code 把允许列表放在各 package.json 的 allowScripts，pnpm 12 把允许列表放在 pnpm-workspace.yaml 的 allowBuilds。两者都在解决“依赖树里的生命周期脚本需要可审计的放行策略”这个问题。

    6.4 打包

    build/ 是打包与发布的中枢：

    • build/gulpfile.vscode.ts 组装主应用，处理 ASAR、NLS、source map、Copilot 运行时、checksums 与 macOS 打包。
    • build/gulpfile.vscode.linux.ts、.win32.ts、.web.ts 分别处理 Linux、Windows、Web 产物。
    • build/lib/electron.ts 下载 Electron 并生成平台模板。
    • build/lib/asar.ts 处理应用归档。
    • build/checksums/ 保存 Electron、Node、WSL、Explorer DLL 等制品的校验和。
    • product.json 负责品牌、协议、下载 feed 与内建扩展清单；Electron 版本由 .npmrc 提供。
    • resources/ 提供各平台图标、.desktop、安装器资源。

    CI 分成两层：build/azure-pipelines/ 负责产品构建与发布，覆盖 linux、win32、darwin、web、cli、copilot、distro 等目录；.github/workflows/ 负责 PR 侧的 Linux/Windows/macOS 测试、CLI 测试、Sessions E2E 与依赖检查。.github/actions/setup-electron/action.yml 用 hashFiles('.npmrc', 'build/checksums/electron.txt') 作为 Electron 缓存键，把“版本文件变化”直接映射到缓存失效策略。

    7. 测试与开发工作流

    test/ 按测试类型拆分：

    • test/unit/：Node、浏览器、Electron 单元测试。
    • test/integration/：浏览器、Electron、Agent Host 集成测试。
    • test/smoke/：UI 冒烟测试。
    • test/automation/：自动化测试基础设施。
    • test/monaco/：Monaco 独立测试。
    • test/scenario/、test/sanity/：场景与发布 sanity 测试。
    • test/componentFixtures/：组件夹具与 Playwright 截图。

    scripts/ 提供 code.sh、code-server.sh、code-web.sh、test.sh、test-integration.sh 等入口。根 package.json 的 compile、watch、test-node、test-browser、build-fast 脚本负责日常开发。.devcontainer 提供 9GB 内存、desktop-lite、Rust、sshd 等特性，适合完整构建与 UI 测试。

    scripts/code.sh 还保留 WSL 分支：未设置 DISPLAY 时会尝试从 Windows 侧推导显示地址。现代 WSLg 已提供 DISPLAY=:0，这个分支通常不会触发；它说明 VS Code 自身也把 WSL 作为一等开发环境处理。

    8. Agent 与扩展生态

    参考树包含一层明显的 agent 工具链：

    • src/vs/sessions/：Agents Window，作为 workbench 之上的新层，拥有独立的 browser/common/electron-browser/contrib/services 和 13 份 Markdown 文档。LAYERS.md 明确规定 sessions 可以导入 workbench，workbench 不能反向导入 sessions。
    • src/vs/platform/ 中的 chat、mcp、agentHost、agentPlugins 等服务目录。
    • src/vs/workbench/contrib/ 中的 chat、mcp、inlineChat、inlineCompletions、remoteCodingAgents 等 contribution。
    • src/vscode-dts/ 的 185 个 proposed API，覆盖 chat、MCP、language model、agent sessions。
    • .github/instructions/ 与 50 个 .github/skills/，AGENTS.md，.agents/skills/launch，.mcp.json，copilot_shim/ 与 extensions/copilot/。

    这层结构把“AI 能力”放进与编辑器、终端、Git 相同的 contribution 体系，同时用 sessions 的独立层约束新增代码的导入方向。对于大型 Electron 应用，这是一种可复用的演进方式：新能力先作为独立层或 extension，再通过明确边界接入主工作台。

    9. 对 Electron 项目与 pnpm 12 的启示

    1. 按进程边界组织目录。 electron-main、electron-browser、electron-utility、node 各自有明确职责，主进程保持轻薄，功能放进 platform/workbench。我们的三个沙箱可以先把 main、preload、renderer 分开，再按需要增加 utility 进程。
    2. 把分层写成可检查的规则。 VS Code 用 ESLint 的 import pattern 检查层间依赖；sessions 的 LAYERS.md 把允许与禁止的导入写成文档。项目规模扩大后，这类规则比口头约定可靠。
    3. 一个版本源头，多种校验。 Electron target 在 .npmrc，Node 在 .nvmrc，依赖在 lockfile，制品在 checksums，缓存键引用这些文件。我们的 pnpm 项目对应 package.json 的 packageManager/devEngines、pnpm-workspace.yaml、pnpm-lock.yaml 与 CI 的 frozen 安装。
    4. 安装脚本要显式放行。 VS Code 用 allowScripts + npm approve-scripts；pnpm 12 用 allowBuilds + pnpm approve-builds。两者都把“依赖能否执行生命周期脚本”作为供应链审查点。
    5. 扩展与内建功能共享 API 边界。 workbench/api 的 mainThread/extHost 配对、vscode.d.ts 与 proposed API，把内建扩展和第三方扩展放在同一套协议上。Electron 应用可以把插件/扩展能力设计成独立进程与 RPC，把功能放在明确边界内。
    6. 构建、打包、资源、测试分开。 build/、resources/、test/、scripts/ 各自有清晰入口，平台差异落在独立 gulpfile 与目录，项目规模增长时仍能保持入口清晰。
    7. 版本文件要能被机器读取。 .npmrc、.nvmrc、package-lock.json、build/checksums/electron.txt 都是构建脚本直接读取的输入；README 只做人读矩阵。我们的项目把 package.json、pnpm-workspace.yaml、pnpm-lock.yaml、.nvmrc 作为机器可读来源。
